# Day 27: Business Logic Flaws in APIs


## I. The Nature of Business Logic
Business Logic is the set of rules that translate real-world operational requirements into code. In an API, this logic dictates the state transitions of a resource (e.g., an "Order" moving from Pending to Paid to Shipped).
Unlike a buffer overflow or an SQL injection, which target the code implementation, a business logic flaw targets the code's purpose.
       - The Core Rule: A Business Logic Flaw occurs when the API performs its technical function correctly but permits a result that violates the intended business process.

---

## II. The API State Machine: Identifying Logic Breaks
In a secure API, the server must strictly enforce the sequence of operations. A logic flaw often manifests as an "illegal state transition."
The "Skip-Step" Vulnerability
Consider a standard e-commerce flow:
1.	POST /api/v1/cart/add (Set Item)
2.	POST /api/v1/checkout/shipping (Set Address)
3.	POST /api/v1/payment/charge (Process Money)
4.	POST /api/v1/order/finalize (Ship Item)
**The Flaw:** If the backend of Step 4 does not verify that a "Success" flag was generated by Step 3 in the database, an attacker can jump directly from Step 2 to Step 4.

---

## III. High-Impact Logic Flaw Categories
### 1. Price and Quantity Manipulation
This occurs when the API trusts the client to define the value of a transaction.
- Vulnerable Request:
**JSON**
```
{
  "item_id": "WS-99",
  "quantity": 1,
  "price_per_unit": 0.01 
}
```
- The Logic Error: The server should retrieve the price from a trusted internal database, not from the user's JSON payload.

### 2. Numerical Boundary Abuse
Exploiting how the backend handles negative numbers or extremely large integers.
- Negative Quantity: {"quantity": -5}. If the backend multiplies price by quantity without validation, it may result in a negative total, potentially adding credit to a user’s balance.
- Integer Overflow: Sending a quantity so large it resets the total to a small number or zero.

### 3. Circular Workflow Abuse (Refund/Coupon Loops)
- Coupon Recycling: Using a "single-use" coupon by triggering a race condition or by exploiting a logic check that only marks the coupon as "used" after the order is confirmed.
- Refund Manipulation: POST /api/refunds with an order_id that was already refunded once, or an order_id belonging to a different user (BOLA + BLF).

---

## IV. Why APIs are Uniquely Vulnerable to BLF
- Headless Nature: Unlike web apps with visual UI flows, APIs are "headless." There is no UI to restrict the order in which a user calls endpoints.
- Trust in the Client: Developers often assume only their "official" frontend will call the API. They forget that an attacker using Burp Suite or Postman can call Step 4 without ever touching Step 1.
- Complex Dependencies: APIs often interact with third-party payment gateways or shipping providers. If the callback logic (Webhooks) is weak, an attacker can spoof a "Payment Successful" message.

---

## V. Professional Workflow Audit Methodology
The Consultant's approach to finding logic flaws is a structured "What If?" analysis.
1.	Workflow Mapping: Create a flowchart of every API request required to complete a business goal.
2.	Constraint Identification: Determine the "Gatekeepers." (e.g., "Which endpoint ensures the user has enough balance?").
3.	Step Skipping: Attempt to call the final "Success" endpoint with no prior session data.
4.	Parameter Stressing: Submit unexpected values (negatives, decimals, nulls) to fields that represent money, weight, or quantity.
5.	State Persistence Testing: Can I start a transaction in v1 and complete it in v2 to bypass a new security check?

---

## VI. OWASP API Security Mapping
- API6: Unrestricted Business Flows: This is the primary mapping. It refers to the failure to limit the execution of business processes, allowing attackers to automate or subvert intended sequences.
- API1 (BOLA): Used as a component of BLF (e.g., manipulating an ID to apply a discount to the wrong account).
- API5 (BFLA): Used to access a "hidden" step in the workflow that should be restricted to internal administrative systems.

---

## VII. Comparison: Technical vs. Logic Flaws
| Feature | Technical Flaw (e.g., SQLi) | Business Logic Flaw |
|------------|------------------------------------|----------------------------|
| Detection | Automated Scanners (DAST/SAST) | Manual Peer Review / Penetration Testing |
| Response Code | Often $500\text{ Internal Error}$ | Usually $200\text{ OK}$ |
| Payload | ' OR 1=1 -- | {"price": 0.00} |
| Remediation | Use Prepared Statements | Re-architect Workflow Validation |

---

### Summary
This module pivots from technical vulnerabilities to Business Logic Flaws (BLF), representing the "expensive" end of the exploit spectrum. Students will learn that an API can be technically perfect—free of injections and with valid schemas—yet remain critically vulnerable if its workflow can be subverted. This session focuses on the systematic analysis of state machines and the identification of trust boundaries where an API incorrectly relies on client-side integrity to enforce business rules.
